1. Executive Summary

1.1 What the system does today

This project is a server-rendered PHP web application that manages a register of students stored in a MySQL database. It implements a complete CRUD cycle plus reporting:

  • Create — a registration form captures first name, last name, email and telephone.
  • Read — a paginated, sortable, searchable table lists all registered students.
  • Update — an edit form pre-filled with an existing student's record.
  • Delete — a link-triggered deletion with a JavaScript confirmation prompt.
  • Export — the full register is streamed to the browser as a downloadable CSV file.

There is no framework, no ORM, no build step and no JavaScript bundle. Every page is a standalone PHP script that connects to the database, executes SQL, and prints HTML. This is deliberately simple and is appropriate for the project's current size; it is also the main constraint discussed in sections 9 and 12.

1.2 Scope clarification: "School Management System"

Important for any developer reading this. The repository is frequently described as a "school management system". As the code currently stands it is precisely one module of such a system: the student registry. There is no authentication, no user roles, no classes, no courses, no teachers, no enrolment, no grades, no attendance and no fees. Nothing in this document should be read as implying those exist. Section 12 sets out the path from the current registry to a genuine school management system.

Stating this plainly matters: the codebase is 6 PHP files and roughly 300 lines. Anyone told to expect a full management platform will waste time looking for tables and modules that were never written.

4. System Architecture

4.1 Architectural style

The application follows the classic page-controller pattern of traditional PHP: each URL is a physical file, and that file contains its own controller logic, data access and presentation. There is no routing layer, no separation of concerns, and no shared layout or template.

The consequence, which a new developer should understand immediately: SQL, business rules and HTML live in the same file. In table.php, lines 1–54 are PHP logic and lines 55–137 are the view. The two halves are separated only by the closing ?> tag.

┌──────────────┐ HTTP request ┌───────────────────────────┐ │ Browser │ ──────────────────► │ Apache → PHP 8 │ │ │ ◄────────────────── │ │ └──────────────┘ HTML / CSV │ form.php table.php │ │ update.php delete.php │ │ export.php │ │ │ │ │ ▼ │ │ connection.php │ └────────┬──────────────────┘ │ mysqli ▼ ┌───────────────────────────┐ │ MySQL: student_db │ │ └── students │ └───────────────────────────┘

4.2 Request lifecycle

Every request follows the same five steps:

  1. Apache maps the URL to a .php file and hands it to the PHP interpreter.
  2. The script includes connection.php, which opens a fresh MySQL connection. Each request opens its own connection; nothing is pooled or reused.
  3. The script inspects $_SERVER['REQUEST_METHOD'], $_GET and $_POST to decide what to do.
  4. It builds an SQL string, executes it through mysqli_query(), and reads the result.
  5. It either sends a Location: redirect (write operations) or echoes HTML (read operations).

Post/Redirect/Get is correctly applied. After a successful INSERT, UPDATE or DELETE, the code calls header("Location: table.php"); exit();. This prevents the browser from re-submitting the form on refresh and duplicating records. It is the strongest design decision in the codebase and should be preserved through any refactor.

5. Database Design

5.1 Reconstructed schema

The repository contains no .sql schema file and no migrations. The structure below was reconstructed by reading every query in the codebase. Shipping an authoritative database/schema.sql is the single highest-value addition you can make to this repository — without it, no one can recreate the database.

Evidence used for the reconstruction:

  • form.php inserts into students(first_name, last_name, email, telephone) — four user-supplied columns.
  • update.php and delete.php filter on id after intval(), so id is an integer key.
  • table.php whitelists exactly ['id','first_name','last_name','email','telephone'] as sortable columns — that is the full column list.
  • export.php writes the header row ID, First Name, Last Name, Email, Telephone and then dumps SELECT * rows directly, which only lines up if the physical column order is id, first_name, last_name, email, telephone.

5.2 Recommended DDL

CREATE DATABASE IF NOT EXISTS student_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE student_db;

CREATE TABLE students (
    id         INT UNSIGNED NOT NULL AUTO_INCREMENT,
    first_name VARCHAR(50)  NOT NULL,
    last_name  VARCHAR(50)  NOT NULL,
    email      VARCHAR(150) NOT NULL,
    telephone  VARCHAR(20)  NOT NULL,
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
                            ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uq_students_email (email),
    KEY idx_students_last_first (last_name, first_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

5.3 Data integrity notes

ConcernAnalysis
Duplicate emailsNothing in the PHP checks for an existing email before inserting. The same student can be registered any number of times. A UNIQUE constraint on email enforces this at the database level, which is the correct place — application checks alone are subject to race conditions.
Telephone as VARCHARCorrect, and deliberately so. Cameroonian numbers are written with a leading +237 and may carry spaces; an integer column would destroy both. Never store phone numbers as numeric types.
Character setconnection.php never calls $conn->set_charset('utf8mb4'). Two consequences: accented characters common in Cameroonian names (é, ô, ç) may be mangled, and mysqli_real_escape_string() escapes according to the wrong charset, which weakens the project's only injection defence.
IndexingSorting is currently permitted on all five columns but only id is indexed. ORDER BY last_name over a large table causes a filesort. The composite index above covers the common alphabetical listing.
Search performanceThe search uses LIKE '%term%'. A leading wildcard cannot use a B-tree index, so every search is a full table scan. Acceptable at a few thousand rows; at school scale, move to a FULLTEXT index.
Audit trailThere is no created_at/updated_at today, so it is impossible to know when a student was registered. The DDL above adds both.

6. Feature Walkthrough

6.1 Create — form.php

The file serves both the form and its handler. The method check at the top decides which:

if ($_SERVER['REQUEST_METHOD'] == "POST") {
    $first_name = mysqli_real_escape_string($conn, $_POST['first_name']);
    // ... last_name, email, telephone
    $sql = "INSERT INTO students(first_name, last_name, email, telephone)
            VALUES('$first_name', '$last_name', '$email', '$telephone')";
    if (mysqli_query($conn, $sql)) {
        header("Location: table.php");
        exit();
    } else {
        echo mysqli_error($conn);
    }
}

Validation is entirely client-side: required attributes and type="email" / type="tel". Those are usability features, not security controls — any client that sends a raw POST bypasses them completely. There is no server-side validation at all.

Note also that the failure branch echoes mysqli_error($conn) straight to the page, leaking the raw database error (table names, column names, constraint names) to whoever triggered it. The same pattern appears in update.php and delete.php.

6.2 Read — table.php

Four concerns are handled in sequence:

Pagination

$limit  = 15;
$page   = isset($_GET['page']) && is_numeric($_GET['page']) ? (int)$_GET['page'] : 1;
$offset = ($page - 1) * $limit;

Sorting

This is handled correctly and is worth highlighting as good practice:

$validColumns = ['id','first_name','last_name','email','telephone'];
$sort  = isset($_GET['sort']) && in_array($_GET['sort'], $validColumns) ? $_GET['sort'] : 'first_name';
$order = isset($_GET['order']) && $_GET['order'] === 'DESC' ? 'DESC' : 'ASC';

Column and direction names cannot be parameterised by a prepared statement — they are part of the SQL grammar, not values. A whitelist is the correct defence, and the code applies it properly with a safe default. Keep this pattern when the rest of the file is migrated to prepared statements.

Search

If ?search= is present and non-empty, the base query is replaced by a four-column LIKE query. The term is escaped with mysqli_real_escape_string().

Rendering

Output is escaped with htmlspecialchars() on every cell and on the search box's echoed value, which blocks stored and reflected XSS on those paths. sortLink() builds the column header links and flips the direction when the same column is clicked twice.

6.3 Update — update.php

The GET branch loads the record; the POST branch writes it back, taking the row identifier from a hidden <input name="id">. Both branches use intval() on the id, which makes the WHERE id = $id clause safe. The four text fields use the same escaping as form.php. See section 10.3 for a real bug in the failure path of this file.

6.4 Delete — delete.php

if (isset($_GET['id'])) {
    $id  = intval($_GET['id']);
    $sql = "DELETE FROM students WHERE id = $id";
    if (mysqli_query($conn, $sql)) { header("Location: table.php"); exit(); }
}

The confirm() dialog in table.php is a convenience for the user, nothing more. The deletion is a GET request, which is a significant design flaw — see section 9.2.

6.5 Export — export.php

The script sets Content-Type: text/csv and Content-Disposition: attachment, then streams rows through php://output rather than buffering the whole file in memory — the right approach for a growing dataset.

Hidden coupling. The header row is written by hand as ['ID','First Name','Last Name','Email','Telephone'], but the data rows come from SELECT *. The two only line up while the physical column order matches. The moment someone adds a created_at column, every exported row silently gains a value with no matching header. Select the columns explicitly instead of using *.

9. Security Review

Findings are ordered by severity. Each states the root cause before the fix, because understanding why a class of bug exists prevents reintroducing it elsewhere.

9.1 CRITICAL No authentication or authorisation

Root cause: no session layer was ever built. Not one file calls session_start().

Impact: anyone who can reach the URL can list every student, edit any record, delete any record, and download the complete register from export.php — full personal data of every student, including emails and phone numbers, with a single unauthenticated GET request. On a local XAMPP install this is contained; the moment it is deployed, it is a data breach.

Fix: add an admin_users table with password_hash()-stored credentials, a login.php, and an auth.php guard included at the top of every protected page that redirects to the login screen when $_SESSION['user_id'] is absent. This is prerequisite work for anything else — build it before adding features.

9.2 HIGH Destructive action exposed over GET (CSRF)

Root cause: delete.php performs a state change in response to a GET request, and no CSRF token is verified anywhere in the project.

Impact: HTTP GET is defined as a safe, idempotent method; browsers, link prefetchers, chat previews and crawlers follow GET links freely. An <img src="http://.../delete.php?id=5"> embedded in any page an authenticated administrator visits deletes student 5 silently. The confirm() dialog offers no protection — it is client-side and is never executed in that scenario.

Fix: convert deletion to a POST form, and verify a per-session CSRF token on every state-changing request:

// on render
$_SESSION['csrf'] ??= bin2hex(random_bytes(32));
echo '<input type="hidden" name="csrf" value="' . $_SESSION['csrf'] . '">';

// on submit
if (!hash_equals($_SESSION['csrf'] ?? '', $_POST['csrf'] ?? '')) {
    http_response_code(403);
    exit('Invalid request.');
}

9.3 HIGH String-concatenated SQL instead of prepared statements

Root cause: every query is assembled by interpolating variables into a string. The defence relied upon is mysqli_real_escape_string().

Current status: to be fair to the code, the escaping is applied consistently and intval() guards every id, so no immediately exploitable injection was found. But this is a fragile position, for three reasons:

  • It depends on a developer remembering to escape every variable, every time. One omission is a full compromise.
  • mysqli_real_escape_string() escapes according to the connection charset, and connection.php never sets one (section 5.3). Charset mismatches are a known route around this function.
  • It offers no protection when a value lands outside quotes in the SQL string.

Fix: prepared statements everywhere. The rewrite of form.php:

$stmt = $conn->prepare(
    "INSERT INTO students (first_name, last_name, email, telephone)
     VALUES (?, ?, ?, ?)"
);
$stmt->bind_param("ssss", $first_name, $last_name, $email, $telephone);
$stmt->execute();
$stmt->close();

Values are then sent to MySQL separately from the SQL text and can never be parsed as SQL. Keep the $validColumns whitelist for ORDER BY — identifiers still cannot be bound.

9.4 MEDIUM No server-side validation

Root cause: validation exists only as HTML5 attributes.

Impact: a crafted POST stores an empty name, a 10,000-character string, or "not-an-email" in the email column. Data quality degrades silently.

Fix: validate on the server before touching the database — trim(), length bounds, filter_var($email, FILTER_VALIDATE_EMAIL), and a telephone pattern appropriate to the target region (for Cameroon, /^(\+237)?6[5-9][0-9]{7}$/ covers current mobile numbering). Re-render the form with the submitted values and the error messages rather than discarding the user's input.

9.5 MEDIUM Database errors printed to the browser

Root cause: echo mysqli_error($conn) in three files, plus die("Connection failed: " . $conn->connect_error) in connection.php.

Impact: schema details, file paths and server configuration are disclosed to an attacker, who gets a free map of the database.

Fix: log the real error with error_log() and show the user a neutral message. In production set display_errors = Off and log_errors = On.

9.6 MEDIUM CSV formula injection in export.php

Root cause: field values are written to the CSV without neutralising leading =, +, - or @.

Impact: a student registered with the name =HYPERLINK("http://evil","Click") is stored harmlessly, but when an administrator opens the export in Excel or LibreOffice the cell is evaluated as a formula. This is a stored attack that fires inside the victim's spreadsheet application, not in the browser.

Fix: prefix any value beginning with those characters with a single quote before writing it.

9.7 LOW Credentials committed to the repository

Root cause: connection.php hard-codes host, user, password and database name, and the file is tracked by Git.

Impact: harmless today (empty XAMPP default), but the pattern guarantees that a real production password will eventually be committed and published.

Fix: move the values into an untracked config.php (or environment variables), commit a config.example.php with placeholders, and add config.php to a .gitignore — the repository currently has none.

10. Known Bugs & Root-Cause Analysis

10.1 HIGH Pagination is wrong whenever a search is active

Where: table.php lines 37–40.

$countResult = mysqli_query($conn, "SELECT COUNT(*) AS total FROM students");
$totalRows   = mysqli_fetch_assoc($countResult)['total'];
$totalPages  = ceil($totalRows / $limit);

Root cause: the count query is unconditional. It counts every row in the table, while the list query above it may have been narrowed by a LIKE filter. The two queries disagree about what "the result set" is.

Observable symptom: with 100 students, searching for a term that matches 3 of them still renders 7 page links. Pages 2 through 7 are empty.

Fix: build the WHERE clause once and apply it to both the SELECT and the COUNT(*). Restructuring the file so the filter is a single variable used by both queries also removes the duplicated SQL.

10.2 MEDIUM A negative or zero page number breaks the listing

Where: table.php line 8.

Root cause: is_numeric('-3') returns true, so $page becomes -3 and $offset becomes -60. MySQL rejects a negative OFFSET, mysqli_query() returns false, and mysqli_fetch_all(false, …) then raises a fatal error. The same happens with ?page=0.

Fix: clamp the value — $page = max(1, (int)($_GET['page'] ?? 1)); — and, once $totalPages is known, clamp the upper bound too.

10.3 MEDIUM update.php crashes on a failed update or a missing id

Where: update.php lines 4–9 and 41–53.

Root cause: $student is only populated inside if (isset($_GET['id'])). The HTML below always runs and always dereferences $student['id']. Two paths reach it undefined:

  • A POST whose UPDATE fails — the code echoes the error, does not exit, and falls through to the form. $student was never set, because there is no $_GET['id'] on a POST.
  • A GET with a non-existent id — mysqli_fetch_assoc() returns null, and on PHP 8.1+ htmlspecialchars(null) is deprecated; accessing null['id'] is a warning that renders an empty form with no id.

Fix: after the fetch, guard explicitly — if no record was found, redirect back to table.php (or render a "student not found" message) and exit(). On the POST failure path, redirect back to update.php?id=$id with the error rather than falling through.

10.4 LOW Searching for "0" returns everything

Where: table.php line 22 — !empty($_GET['search']).

Root cause: in PHP, the string "0" is falsy, so empty("0") is true and the search branch is skipped. This is one of PHP's classic type-juggling traps.

Fix: test the string explicitly: if (isset($_GET['search']) && trim($_GET['search']) !== '').

10.5 LOW The export header row can drift from the data

Covered in section 6.5. Replace SELECT * with an explicit column list.

10.6 LOW Pagination renders every page as a link

Where: table.php lines 122–127.

Root cause: the loop runs from 1 to $totalPages with no window. At 3,000 students that is 200 links on every page load.

Fix: render a sliding window (first, last, and a few pages either side of the current one).

12. Improvement Roadmap

Three phases, ordered so that each one rests on the previous. Do not start phase 3 before phase 1 is complete.

Phase 1 — Harden what exists

  • Sessions, login, logout, password hashing with password_hash() / password_verify().
  • An auth.php guard included at the top of every protected page.
  • Prepared statements throughout; set_charset('utf8mb4') in the connection.
  • CSRF tokens; delete converted to POST.
  • Server-side validation with errors re-rendered into the form.
  • database/schema.sql, .gitignore, and credentials moved out of version control.
  • Fix bugs 10.1 – 10.4.

Phase 2 — Restructure for growth

  • Add index.php as a proper entry point.
  • Introduce includes/header.php and includes/footer.php so navigation and the stylesheet link live in one place instead of being duplicated per file.
  • Move data access into functions (getStudents(), findStudent(), createStudent(), updateStudent(), deleteStudent()) in a students.php model file, so pages stop writing SQL directly. This single change is what makes the codebase testable.
  • Switch to PDO, or at least settle on one mysqli style — the code currently mixes the object-oriented constructor with procedural query calls.
  • Make the layout responsive; consolidate the two stylesheets into one.

Phase 3 — Become a school management system

Only at this point does the "school management" name become accurate. Suggested entity model:

students ──< enrollments >── classes ──< class_subjects >── subjects │ │ │ └── teachers ├──< attendance ├──< grades (student_id, subject_id, term, score) └──< fee_payments (student_id, term, amount, paid_at, method) users (id, username, password_hash, role) role ∈ {admin, teacher, secretary}

Build these one module at a time, each with its own CRUD, each behind the authorisation layer from phase 1. For a Cameroonian deployment, two things deserve early attention: bilingual (English/French) labels, and Mobile Money reconciliation in the fees module — both are far easier to design in from the start than to retrofit.

Appendix B — Glossary

TermMeaning in this project
CRUDCreate, Read, Update, Delete — the four operations this application implements over the students table.
Post/Redirect/GetResponding to a successful POST with a redirect, so refreshing the page does not resubmit the form. Used after every write here.
Prepared statementAn SQL statement sent to the database with placeholders, whose values are transmitted separately and therefore can never be interpreted as SQL. Not yet used in this project.
CSRFCross-Site Request Forgery — making a logged-in user's browser issue a state-changing request without their intent. delete.php is currently vulnerable.
XSSCross-Site Scripting — injecting script through stored or reflected data. Mitigated here by htmlspecialchars() on output.
Offset paginationFetching a page of rows with LIMIT and OFFSET. Simple, and what table.php uses.
Page controllerThe architectural pattern where each URL maps to one file that handles logic and rendering together.
Formula injectionA stored value beginning with =, +, - or @ that a spreadsheet program evaluates as a formula when the exported CSV is opened.
